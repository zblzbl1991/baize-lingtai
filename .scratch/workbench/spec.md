# Spec: Workbench — Work Items for Pi Web

Status: ready-for-agent

Revised: 2026-10-06 after design review. This spec defines the intended behavior; the feature is not implemented yet.

Glossary: see `CONTEXT.md` (Work Item, Workbench, Project, Association, Unassociated Session, Work Item Outputs, Completed Work Item). Direction: see `docs/adr/0007-adopt-workbench-domain-freeze-baize-buddy.md`.

## Problem Statement

A user of Pi Web usually has several ongoing goals at once — a feature being built, a bug being chased, a document being drafted — but the sidebar only organizes sessions by Project and recency. Within a busy Project, sessions pile up chronologically; coming back to "that thing I was working on last week" means hunting through the list and reconstructing context by memory. The files a goal produced are even harder to find afterwards: they are scattered across the session transcript and the working tree, and once committed they leave no visible trace in Pi Web.

## Solution

Pi Web adopts the Work Item (工作目标) concept: a durable, outcome-oriented unit of work inside one Project that the user names, groups sessions under, and can complete and reopen. A new Workbench (工作台) view — entered from the top bar, replacing the chat area in place — lists Work Items across all Projects, showing each item's sessions for one-click resumption and its Outputs (产出): files with supported write evidence in currently associated sessions, with current working-tree diffs where available. A session belongs to at most one Work Item. Association comes from an explicit save/attach, starting a session from the Work Item, or inheriting the source Association on fork; existing sessions are never associated automatically. Explicitly attaching a session includes its earlier supported writes in Outputs. Unassociated sessions behave exactly as they do today.

## User Stories

1. As a user, I want to create a Work Item in one of my Projects, so that I can name a goal and start organizing work under it.
2. As a user, I want to save an existing session as a new Work Item, so that work I already did becomes organized without redoing it.
3. As a user, I want the Work Item name prefilled from the session's title when I save a session as a Work Item, so that I don't have to retype what pi already named.
4. As a user, I want to attach an existing session to an existing Work Item, so that related conversations live under one goal.
5. As a user, I want a session to belong to at most one Work Item, so that "which goal is this session part of" is never ambiguous; if the session is already associated, attaching moves it explicitly.
6. As a user, I want sessions I start from inside a Work Item to be associated with it automatically, so that I don't repeat a manual step every time.
7. As a user, I want a Workbench view listing Work Items across all my Projects, so that I can see every active goal at a glance.
8. As a user, I want Work Items grouped by Project in the Workbench, so that items for different working directories stay separable.
9. As a user, I want to open a Work Item and see its sessions, so that I can pick up the conversation I left off.
10. As a user, I want to resume a Work Item by clicking its most recent session, so that returning to a goal is one action.
11. As a user, I want running-session indicators on the sessions shown inside a Work Item, so that I can tell what is currently active.
12. As a user, I want to mark a Work Item as completed and reopen it later, so that finished goals stop demanding attention without becoming unreachable.
13. As a user, I want to filter the Workbench list by in-progress and completed items, so that completed work stays reviewable but out of the way.
14. As a user, I want to rename a Work Item at any time, so that the name can follow what the work turned out to be.
15. As a user, I want to detach a session from a Work Item, so that I can move it elsewhere or leave it unassociated — and I want the move to be an explicit action, never a side effect.
16. As a user, I want forking a session inside a Work Item to keep the fork associated with the same Work Item, so that branching doesn't silently drop work from its goal.
17. As a user, I want deleting a session to detach it from its Work Item while the Work Item survives, so that cleaning up transcripts never destroys my organization.
18. As a user, I want to delete a Work Item without deleting its sessions, so that removing a goal is reversible in practice — the sessions return to the Project's ordinary list.
19. As a user, I want each Work Item to show its Outputs — the files its associated sessions wrote — so that I can find the results of the work without replaying the transcript.
20. As a user, I want to open a written file from the Outputs list in the existing file viewer, so that I can review results in place.
21. As a user, I want a current working-tree diff for Output files that are still uncommitted in their checkout, so that I can review their current changes without mistaking the diff for changes exclusive to this Work Item.
22. As a user, I want committed or deleted Output files to remain listed as paths, so that the historical record of what was produced stays visible even after the changes land.
23. As a user, I want the Workbench view state to survive a page refresh and be shareable via URL, so that "my workbench" behaves like the rest of Pi Web's navigation.
24. As a user with Unassociated Sessions, I want them to behave exactly as they do today — same list, same ordering, same actions — so that the Workbench is purely additive.
25. As a Chinese-language user, I want all Workbench text available in zh-CN and zh-TW, so that the feature is not English-only.
26. As a mobile user, I want the Workbench view usable on a narrow viewport, so that reviewing goals on the phone works.

## Implementation Decisions

### Work Item state and persistence (01)

- **Record.** `id` (uuid), server-derived `projectKey`, canonical `projectRoot`, `name`, `status` (`in-progress` | `completed`), `createdAt`, `updatedAt`, nullable `completedAt`, and unique `sessionIds`. Project identity reuses `resolveProject()` and `projectIdentityKey()`; main checkout and linked worktrees share a key. Paths retain their original filesystem form; identity keys are for equality only.
- **Ordering.** Items sort by `updatedAt` descending, then id ascending. Member sessions sort from current session metadata by `modified` descending, then id ascending; stored array order is not the activity authority. Ordinary session activity does not rewrite Work Item timestamps. Real name/status/Association changes update `updatedAt`; no-ops do not. Completing sets `completedAt`; reopening clears it; repeated status requests preserve timestamps.
- **Completion.** Status is organizational and does not change native session permissions. Viewing, prompting, attaching, starting, or forking a session leaves a completed Work Item completed. Only an explicit status action reopens it; completed detail exposes that action.
- **Authoritative store.** One versioned `pi-web-work-items.json` in `getAgentDir()` (respects `PI_CODING_AGENT_DIR`). Reuse `writePrivateFileAtomicSync()` and a lockfile-guarded read-modify-write, with serialization within the process. Reread and validate the latest disk contents under the lock; cache only validated snapshots, keyed by store path and refreshed when the disk fingerprint changes. This is user data, so the session index's best-effort persistence policy does not apply.
- **Failure semantics.** Only a genuinely absent store initializes empty. Malformed JSON, invalid records, unknown schema versions, permission errors, and failed writes return typed errors and preserve existing bytes; the UI offers retry without reporting success. Do not overwrite an unreadable store with an empty one. A valid duplicate Association from a hand edit uses the lexicographically smallest Work Item id as the deterministic read-side winner; reads do not rewrite disk. A successful mutation normalizes duplicates under the lock. See lifecycle rules below for missing sessions.

### API and Association (01–02)

- **Collection/item routes.** `GET /api/work-items` returns `{ workItems }` including each item's current Association view. `POST` creates `{ projectRoot, name?, sessionIds? }`; each initial session must currently be unassociated. `PATCH /api/work-items/[id]` handles `{ name?, status? }`. `DELETE` removes only the item and its Associations; native session files survive. Use the existing route JSON conventions, with structured `code` errors: invalid request `400`, missing resource `404`, Association conflict `409`, and store failure `500`/`503` as appropriate. Enforce absolute project paths, valid UUIDs/statuses, and bounded names and arrays; use localized untitled names supplied by the UI for fresh items. The server derives Project identity and validates every source session against it.
- **Dedicated Association intent.** `POST /api/work-items/[id]/sessions` takes one `{ sessionId, expectedWorkItemId: string | null }`. `null` means attach only if currently unassociated; another id means the user confirmed moving from that exact source. Attaching to the current item is an idempotent no-op. Otherwise compare the expected source under the store lock and return `409 { code: "association_conflict", currentWorkItemId }` on mismatch. A move removes from the old item and adds to the new one in the same store write. The client refreshes and asks for a new confirmation after a conflict, rather than repeating the move silently.
- **Detach/save-as.** `DELETE /api/work-items/[id]/sessions/[sessionId]` removes only that item's Association; it is a no-op if the session is no longer there and cannot detach it from another item. Save-as atomically creates an item and associates an unassociated session, prefilled from its title; an already-associated session uses the explicit move flow instead of silently creating a competing item. Initial multi-session creation validates all sessions before writing anything.
- **Project checks.** The picker lists only same-Project items, but the server independently validates the actual session's Project, including worktrees and Windows path equivalence. A Work Item record does not grant file access; existing cwd validation and file/Git authorization remain the access boundary.

### Navigation and session lifecycle (01–03)

- **View.** AppShell gains `activeView: "chat" | "workbench"`. Workbench replaces the main chat area while keeping sidebar and file/terminal tabs available. `?view=workbench` participates in initial restore and every URL-writing path, including remembered session/cwd restoration, with the existing write-before-replace guard. Preserve the selected session/cwd when toggling views. Explicit session selection or new-session navigation returns to chat. Switching to Workbench preserves composer drafts and does not abort native agent runs; returning reconnects through the existing session reconciliation.
- **Resume.** Each nonempty item offers one-click resume of its most recently modified available session, using the same ordering as detail. Empty items offer New session. Missing/unreadable members cannot displace an available session. Creating a session from an item defaults to its `projectRoot`; opening an existing session preserves that session's actual cwd/worktree.
- **Creation intent.** Bind a pending `workItemId` to the composer's draft identity, not a global current selection. Pass it to `/api/agent/new` whenever that draft initializes a real session, including non-prompt `ensure_session` for System/Tools inspection. The server validates the item and Project, creates the real session, and persists its Association before full success or dispatching the first prompt. Client promotion refreshes/selects the session; it does not perform the authoritative attach. Normal new-session drafts have no pending Association. Switching or parking drafts preserves each draft's own intent until submitted or explicitly discarded.
- **Fork/clone.** The server's `fork`, `fork_branch`, and `clone` paths inherit the source Association and add the generated session id without detaching the source. Capture the source Association before creation and revalidate it when committing; a concurrent move/delete returns a recoverable conflict instead of silently following the new owner. Unassociated sources produce unassociated children. In-session `navigate_tree` stays within the existing Association. Client callbacks only refresh and select.
- **Partial failure.** Native session creation/fork and the store are separate writes, not a transaction. If a session was created but Association persistence fails, return `code: "association_pending"` with its real `sessionId`, intended `workItemId`, and a cause (`association_conflict`, missing item, or store failure); use `409` for a conflict and `500`/`503` for store failures. Do not claim full success or dispatch a first prompt. Keep the resulting native session accessible. Recovery retries only the Association for that id and repeats conflict validation; a deleted target requires explicit selection of another item. Recovery never automatically creates/forks again or resends a prompt. A browser disconnect does not prevent the server from finishing an already accepted Association write. A server crash between the two writes may leave a persisted unassociated session discoverable for explicit attach; unpersisted empty runtimes follow native restart behavior and are not promised recovery.
- **Liveness/deletion.** Lazy filtering checks persisted sessions together with live wrappers, including transient ones. A cache miss, partial catalogue, permission failure, or temporary unreadability is not proof of deletion. Filter only confirmed absent ids after authoritative discovery; retain unresolved Associations with an unavailable state. Reads do not destructively prune the stored list. In-app deletion strips every id actually deleted, including cascaded subagents, after file deletion; failed cleanup is reported and retried by lazy filtering. Empty Work Items survive. Subagent sessions do not inherit automatically; their explicit Associations follow the same rules as other sessions.

### Outputs (04)

- **Projection contract.** `GET /api/work-items/[id]/outputs` lazily returns `{ outputs, incomplete, reasons }`. Rows carry `filePath`, `sourceSessionId`, `sourceCwd`, nullable `checkoutRoot`, nullable `lastWrittenAt`, current file state, and `diffAvailable`. Rows sort by known last-write time descending then path ascending, with unknown times last; equal-path evidence retains its latest determinable source, with session id breaking ties. Scan raw message entries across all branches, including entries compacted out of current context; forked copies are deduplicated by resolved local path. Include supported writes before explicit attach. Detaching/deleting a session removes its contribution on refresh; this feature retains paths only while supported evidence remains in currently associated transcripts.
- **Supported evidence.** Normalize raw tool-call fields and require a paired successful result for top-level pi `write`/`edit` and the supported local `apply_patch` contract, reusing its applied-files/partial-failure handling. Extract successful nested pi `write`/`edit` from the SDK's structured `toolResult.nestedCalls.calls` (`status: "ok"` and full `arguments`), even if the parent Code mode call later errored. Nested patch calls without applied-file results, shell-created files, remote writes, and namespaced MCP write/edit names without nested local coding-tool evidence are outside initial coverage. Tool names alone, reply text, scripts, `details.calls` display strings, and existing coincident local files are not local-write evidence. MCP name variants get negative fixtures; a future local MCP adapter requires an explicit evidence contract before expanding coverage.
- **Paths/access.** Resolve each relative tool path against its source session's cwd, never the Work Item's main root. Deduplicate using server path equality rules; identical relative names in separate worktrees remain separate files. Include files only within that Project's actual checkouts, checking resolved links against existing access rules. Removed worktree paths stay identified at their original locations, not rebound to the main checkout. Outside-Project or denied paths are omitted with an incompleteness reason; displaying a row never grants new file access.
- **Bounds/freshness.** Set explicit limits for session count, bytes/line, total scan time, and response size using session search as prior art. Any exceeded limit, unreadable source, or supported nested-call record with `complete: false`/omitted arguments sets `incomplete` and a reason. The UI labels partial results even when the list is empty. Cache extraction against store membership and source session fingerprints, including live revisions; refresh on entry to detail and after session completion/Association edits. Query current file/Git states again on Outputs refresh independently of the transcript cache, so an external edit, commit, or deletion changes the displayed state without a new session entry. A cached result cannot hide new writes or changed membership.
- **Current file state.** Resolve the file's own checkout root from its source cwd and query Git there (a session subdirectory would otherwise hide sibling-file changes). Existing changed files use the existing diff route/viewer when it supports a diff; binary/unsupported diffs show that limitation. Clean tracked files are labeled clean, not asserted to be the original committed output. A missing/deleted file remains a path with no open/diff action; non-Git files remain openable without a diff. Git lookup/read failures have explicit unknown/unavailable states. The UI calls diffs current working-tree changes: another session, goal, or user may have contributed to them. The viewer/tab retains the row's checkout root (source cwd for non-Git files) and sourceSessionId independently of the currently selected chat Project.

### Naming, locales and demo (01–05)

- Save-as prefills the session's current title; a fresh Work Item defaults to a localized untitled placeholder. Rename is always available. Work Item operations store their metadata outside native pi transcripts.
- New strings, including store errors, Association conflicts, recovery, partial Outputs, and file states, live under `workbench.*` in en, zh-CN, and zh-TW.
- The static GitHub Pages demo reuses AppShell and gains minimal Work Item/Association/Outputs mocks. BaizeBuddy prototypes inform layout only; use Pi Web's existing theme tokens and responsive conventions.

## Testing Decisions

- Test external behavior only — store semantics, API responses, extracted file lists, view state transitions — never internal call order.
- **Store seam.** Injectable path and session discovery; temp-directory behavior tests cover CRUD/order/status no-ops, concurrent mutations, disk cache freshness, duplicate Associations, all-or-nothing save-as/moves, corrupted/unknown schemas, and write failures preserving bytes. Include transient-live, confirmed absent, and unreadable-source cases.
- **Outputs seam.** Hand-built raw JSONL fixtures cover normalization, successful/failed/partial patch calls, nested local writes, parent errors, unsupported MCP variants, branches/compaction/fork copies, path resolution across subdirectories and two worktrees, Windows deduplication, access filtering, and incomplete scans. Test current file states independently of extraction.
- **Routes/lifecycle.** Import behavior through jiti with stubbed session/store dependencies; test server Project validation, stale move confirmation, creation/fork without a browser callback, first-prompt gating on Association failure, recovery without duplicate native operations, and cascaded deletion. Static source assertions may supplement these tests but do not replace observable error/response behavior.
- **View/e2e.** AppShell restore and draft/view transitions follow the existing test family; cover one-click resume, completed status remaining explicit, unavailable and partial-result states, mobile behavior, and file/diff routing while another Project is selected. The existing e2e runner covers create → associate fixture write session → Outputs → complete → refresh/reopen; include a cross-worktree path/diff scenario.

## Out of Scope

- Everything ADR 0007 excludes: Ask/Full Access permission language, Run/Execution Attempt, Task Skills, OfficeCLI — Pi Web keeps pi's native tool presets.
- A third lifecycle state (archived), agent-proposed completion, dashboards or boards (a fuller dashboard is only a possible later step), realtime cross-tab sync of Work Item edits (a refresh is enough).
- Any sidebar integration: the Workbench is the separate cross-Project view; the sidebar's session list stays untouched.
- Per-session manual rename; Work Item descriptions/notes; Artifact versions, confirmations, or a provenance ledger; BaizeBuddy's "no retroactive artifact claiming" rule stays deferred until outputs attribution deepens.
- Outputs for shell-created files, unsupported nested patch calls, or MCP/remote writes without local coding-tool evidence; historical committed diffs and retained file contents.
- New subagent inheritance policies, automatic continuation-context injection, or a distributed transaction between pi session files and the Work Item store.

## Further Notes

- BaizeBuddy is frozen as a read-only reference (ADR 0007); its Workbench HTML prototypes and UX review documents are design references for the view's look, not contracts.
- The store shares Pi Web's private atomic-write and versioned-file conventions; its authoritative-data error handling differs from the rebuildable session index.
- Running sessions appear inside Work Items through the existing session-list merge with the running-registry snapshot — no separate running-state plumbing.
- Ticket graph remains `01 → 02 → {03, 04} → 05`. Completion of the store/Association contracts is required before lifecycle or Outputs implementation consumes them.
